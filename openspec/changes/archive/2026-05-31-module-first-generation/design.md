## Context

project-arch-reverse 的当前生成流程是"先根后模块"：扫描阶段输出依赖矩阵和图表后，策略 A 先写入 21 章根架构文档，再逐个写入 12 章模块文档。根文档的 7/21 个章节（§6 依赖图、§7 依赖分析、§8 模块介绍、§12 业务流程图、§13 数据库设计、§14 类图、§20 模块索引）的内容天然来自模块文档，先写根文档导致凭空生成再反复修正。CP2.5 自检有 3 次上限，未通过时可带残留问题退场。

## Goals / Non-Goals

**Goals:**
- 模块文档优先生成，根文档延迟到所有模块完成后聚合生成
- 模块按依赖拓扑排序分批次，同层无依赖模块可并行生成
- 根文档 §12 全量汇总所有核心功能（含跨模块综合分析），不依赖推断
- CP2.5 自检无次数上限，必须全部通过才能结束
- 不可自动修复的阻塞项通过 CP3 委托处理，处理完成后回归 CP2.5

**Non-Goals:**
- 不改变扫描阶段逻辑（CP0/CP1/扫描步骤不变）
- 不新增文档类型或章节
- 不改变日志文档生成流程的顺序位置
- 不引入真正的并行执行引擎（同层"并行"是逻辑分组，实际由 Agent 串行调用）

## Decisions

### D1: 拓扑排序算法选型

**选择**: Kahn 算法（BFS 分层）

**原因**:
- 自然产出层级分组（Layer 0, 1, 2...），同层模块无依赖可独立生成
- 时间复杂度 O(V+E)，与依赖矩阵规模匹配
- 循环依赖检测已存在于扫描阶段，可直接复用
- 备选 DFS Tarjan 强连通分量算法也能分组但复杂度高，Kahn 更直观

**处理循环依赖**: A⇄B 形成环时，将 A 和 B 合并为同一虚拟层，同层并行生成
**跨层引用**: 上层的模块文档产出后，下层模块可在生成时引用其文档内容作为上下文

### D2: 生成阶段重新编排

**旧流程（策略 A）**:
```
mkdir docs/architecture/ → 根文档 → mkdir modules/ → 模块文档×N → mkdir logs/ → 日志文档
```

**新流程（策略 A）**:
```
mkdir docs/architecture/ → mkdir modules/
→ 【Layer 0 模块文档】 → 【Layer 1 日志文档】
→ 【Layer 1 模块文档】 → 【Layer 1 日志文档】
→ ...
→ mkdir logs/
→ 【根文档 — 聚合生成】
```

策略 B/C 同理翻转：先更新变化模块 → 再重新聚合根文档。策略 D 不变。

### D3: 根文档 §12 聚合模式结构

```
§12 主要业务流程图
├── 12.1 整体业务概览 (Mermaid flowchart 跨模块全景，节点标注"详见某模块"）
├── 12.2 核心功能索引表 (功能ID | 功能名 | 所属模块 | 类型 | 本文档节号)
├── 12.3 模块级核心功能 (按拓扑序逐个模块)
│   ├── 12.3.1 {模块A} 核心功能
│   │   ├── 12.3.1.1 核心功能1 [独立时序图 + 步骤详解 + 代码片段]
│   │   └── 12.3.1.2 核心功能2 [同上]
│   ├── 12.3.2 {模块B} 核心功能
│   └── ...
└── 12.4 跨模块综合功能
    ├── 12.4.1 端到端功能1 [跨模块时序图，多模块参与者]
    └── 12.4.2 端到端功能2 [同上]
```

**聚合来源映射**:

| 根文档节 | 聚合来源 |
|----------|---------|
| 12.1 整体概览 | 导航分析 + 模块§4核心业务流程 |
| 12.3 模块级核心功能 | 对应模块文档 §6（每功能独立时序图+步骤详解+代码） |
| 12.4 跨模块功能 | 综合多模块 §4+§5+§6 分析端到端流程 |

### D4: CP2.5 自检硬门禁设计

**6 步自检清单**:
```
1. 模块覆盖与完整性  — N个构建文件识别 = M个模块文档 ✓，每文档12章完整
2. 模块间依赖一致性  — A模块§3声明依赖B → B模块存在且依赖方向正确
3. 根文档21章完整性   — 21章俱全，无占位符
4. 根文档聚合正确性   — §6 ↔ 模块§3，§12 ↔ 模块§6，§13 ↔ 模块§7，§14 ↔ 模块§11
5. 核心日志完整性     — 核心模块均有5章日志文档
6. 聚合图表交叉验证   — §12时序图 ↔ 模块§6时序图一致（步骤数、参与者、调用顺序）
```

**判定矩阵**:

| 发现类型 | 处理 | 循环策略 |
|----------|------|---------|
| 缺失章节/文档 | 自动补充 → 重新自检 | 同问题第3次失败 → 阻塞 |
| 依赖不一致 | 自动修正 → 重新自检 | 同问题第3次失败 → 阻塞 |
| 聚合不一致 | 重新聚合 → 重新自检 | 同问题第3次失败 → 阻塞 |
| 架构判断需领域知识 | 标记阻塞 → 委托 CP3 | CP3 处理完回归 |
| 非标准结构无法解析 | 标记阻塞 → 委托 CP3 | CP3 处理完回归 |

**防死循环**:
- 同一检查项的同一问题自动修复 3 次仍失败 → 标记阻塞委托 CP3（不再自动修复）
- 全轮自检 5 轮后仍有阻塞项 → 暂停请求用户决策（继续/降级/接受）
- 用户可通过 CP3 明确接受残留后跳过检查项

**CP2.5 ↔ CP3 关系变化**:
- 旧：CP2.5 → CP3 线性流程
- 新：CP2.5 可能触发 CP3 委托 → CP3 完成 → 回归 CP2.5

## Risks / Trade-offs

| Risk | Mitigation |
|------|-----------|
| 模块数量多时拓扑排序耗时 | 限制扫描深度（已有≤5），过滤非核心模块 |
| 循环依赖合并同层可能导致时序图参与者跨层引用不完整 | 循环依赖块中 A 引用 B 时只需标注"参见 B 模块文档"，根文档 §12.4 统一分析 |
| 根文档聚合时大量内容可能超长 | §12.3 模块功能引用模块文档链接，不逐字复制，仅复制时序图+步骤表核心内容 |
| 硬门禁下极端情况可能自检循环过多 | 防死循环策略中 5 轮上限+用户决策作为安全阀 |
| CP2.5→CP3→CP2.5 回归可能打断用户工作流 | CP3 委托定向处理特定阻塞项，完成后自动回归，不需要用户手动触发 |
