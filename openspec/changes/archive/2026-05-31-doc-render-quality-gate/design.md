## Context

项目架构逆向工程 skill 的核心交付物是 Markdown 文档。当前在 Mermaid 图表、表格、代码块等方面只有人工目检（CP6 一条 check），没有自动预检。实际执行中发现大量渲染错误。本设计引入双门禁质检机制：CP4 生成时立即检查（门禁1，单文档局部）+ CP6 自检时全量扫描（门禁2，跨文档全局）。不可自动修复的标记跳过并在报告中体现。

## Goals / Non-Goals

**Goals:**
- 生成后的文档在任何 Markdown 渲染器中不会出现语法错误
- Mermaid 10 种常见错误模式全部自动检测 + 自动修复
- 表格、代码块、链接自动校验
- 不可修复的渲染问题标记跳过，报告透明

**Non-Goals:**
- 不校验文档内容的业务正确性（那是 CP6 其他步骤的事）
- 不使用外部 Mermaid 渲染器做在线验证（太重）
- 不修复 Markdown 内容中的错别字或语义错误

## Decisions

### Decision 1: 双门禁而非单门禁

**选择**: CP4 生成时质检（门禁1）+ CP6 自检时二次校验（门禁2）。

**理由**:
- 门禁1 保证单文档质量，用户 CP5 看到的就是干净的
- 门禁2 做全局检查（链接有效性需要全量文件系统扫描）
- 两层互补：门禁1 修局部，门禁2 验全局

### Decision 2: 正则扫描而非 Mermaid 解析器

**选择**: 使用正则表达式对 Mermaid 代码块执行结构化扫描，不引入 npm 包做完整解析。

**理由**:
- Mermaid 解析器的依赖（puppeteer/无头浏览器）太重
- 10 种错误模式是已知有限集，正则足以覆盖
- 正则更轻量，无需额外安装

### Decision 3: 自动修复 → 尽力修 → 跳过 三级处理

**选择**: 发现错误时按可修复性分三级：
1. 明确可修 → 自动修复（如加引号、转义、补代码块闭合）
2. 部分可修 → 尽力修复后标记跳过（如表格缺列，尝试补齐但可能不完美）
3. 无法修复 → 标记跳过入报告（如空章节需要内容）

**理由**: 不阻塞流程，但所有跳过项对用户可见。

## Risks / Trade-offs

- [风险] 正则检测可能漏掉边缘 case
  → 缓解：双门禁 + 后续实际使用中积累 case 补充规则
- [风险] 自动修复可能引入新错误
  → 缓解：修复后重新扫描该块，确认通过
- [权衡] 质检增加约 10-20% 生成时间 vs 消弭全部渲染错误
  → 选择消弭：渲染错误是交付物质量底线
